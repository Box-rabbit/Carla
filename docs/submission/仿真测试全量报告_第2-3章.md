# 仿真测试全量报告

## 2. 测试场景与任务设置

本项目基础赛道测试基于 `CARLA 0.9.10.1` 搭建，统一使用 `Town05` 地图进行长路线综合场景验证。仿真主循环采用固定步长 `0.05s`，即 `20Hz` 运行频率；路线、场景触发器、语音事件和评测日志均在同一时间基准下记录。整体测试入口采用 `run_benchmark.py` 统一编排，输入由路线 `XML`、场景注解 `YAML`、场景配置文件、离线语音匹配文件和逐帧日志共同组成，输出包括 `frames.jsonl`、事件列表、单场景报告以及后续汇总报表。

三类测试场景均采用“路线连续驾驶 + 关键事件触发 + 结果判定”的统一组织方式。路线文件定义自车全局行驶轨迹，场景配置定义天气、任务窗口、控制参数和成功/失败条件，语音匹配文件定义某条音频在路线进度上的触发位置。测试期间记录每一帧的自车位置、速度、转向、制动、路线进度、交通违规、语音触发时间、识别结果和场景附加状态，为后续计算任务完成率、语音识别准确率、多模态语义对齐精度和响应延时提供原始依据。

### 2.1 基础操控场景

基础操控场景采用 `S11_basic_control_scene1_5km` 长路线工况，地图为 `Town05`，天气为 `ClearNoon`，测试路线长度约 `5.28km`。道路环境为晴天白天的城市主干道，视野良好，无动态障碍物干扰，重点验证系统对基础驾驶动作的解析、执行和连续驾驶稳定性。场景运行上限时间设置为 `900s`，后处理保持时间为 `5s`。

该场景需要连续完成保持车道、真实路口右转、真实路口左转、左变道、提速到 `80km/h`、减速到 `30km/h` 和长路线完成等子任务。动作窗口由路线进度约束：右转窗口约 `95m-185m`，左转窗口约 `185m-305m`，左变道窗口约 `420m-730m`，提速窗口约 `1500m-2500m`，减速窗口约 `2900m-3500m`。成功判定要求无碰撞、无闯红灯、无车道侵犯、路线完成率达到设定阈值，并完成全部规定子任务。

基础操控场景的测试目标主要包括四点：第一，验证文本或语音中的基础动作是否能被正确映射为驾驶行为；第二，验证速度控制和转向控制在长路线上的稳定性；第三，验证路线跟踪、交通规则遵守和动作完成判定的一致性；第四，验证语音触发后系统是否能在限定延时内完成基础动作响应。

### 2.2 复杂避障场景

复杂避障场景采用 `S12_complex_obstacle_scene2_8km` 长路线工况，地图为 `Town05`，天气为 `CloudySunset`，路线长度约 `8.08km`。场景环境为阴天傍晚的城市次干道，包含十字路口、公交站以及多类交通参与者，重点验证系统在低光照和混合交通流条件下，对组合语义指令和多模态感知结果的联合决策能力。场景运行上限时间设置为 `1200s`。

该场景串联三段关键任务。第一段为行人横穿减速避让，动作窗口约 `300m-480m`，测试系统对横穿行人识别、减速触发和让行完成的能力。第二段为慢车左变道超越，动作窗口约 `1050m-1280m`，测试系统对前车阻塞、相邻车道可用性和超越后回归原车道的联合判断能力。第三段为公交站谨慎通过，动作窗口约 `1760m-1980m`，测试系统对公交站附近行人活动、靠站车辆和安全通行窗口的鲁棒处理能力。

成功判定要求完成 `8km` 连续驾驶，场景关键动作无遗漏，无碰撞，违规次数受控，并完成 `avoid_pedestrian`、`overtake_slow_vehicle`、`return_to_original_lane`、`bus_stop_caution` 和 `finish_8km_route` 等预定义子任务。该场景同时用于验证多视角图像、`LiDAR` 点云和车辆状态在复杂语义约束下的协同效果。

### 2.3 极限应急场景

极限应急场景采用 `S13_extreme_emergency_scene3_6km` 长路线工况，地图为 `Town05`，路线长度约 `6.00km`。天气采用自定义雨夜参数 `CustomHardRainNight`，包括高云量、降雨、路面湿滑、风、雾和夜间低光照等条件，重点验证系统在恶劣环境下的应急响应速度、安全兜底和多模态鲁棒性。场景运行上限时间设置为 `900s`。

该场景包含两类关键高风险事件。第一类为突发车辆加塞，应急窗口从约 `1120m` 激活，前车在约 `1260m` 位置从相邻车道切入本车道，要求系统在极短时间内完成危险识别、紧急制动和安全跟随。第二类为施工路段减速并道，相关窗口从约 `2480m` 开始，系统需要识别施工锥桶、受限车道和施工人员活动范围，减速并道至左侧车道，通过后再回归正常路线。场景成功判定要求无碰撞、无路线偏离、无红灯违规，并满足最大响应延时、最小安全距离、目标路线进度和各阶段保持时长约束。

该场景重点检验三方面能力：第一，系统能否在雨夜低能见度环境下保持稳定感知；第二，系统能否对“保持安全车速”“突发车辆加塞，紧急避让”“施工路段，减速并道至左侧车道”等模糊或应急语义给出安全响应；第三，系统能否在纵向制动、横向并道和任务完成率之间合理平衡，以优先保证安全。

### 2.4 语音触发方式与测试流程

本项目采用“离线语音匹配 + 路线进度触发”的统一测试方式。所有语音样本先通过离线处理生成 `json` 识别结果和 `wav` 音频索引，再通过 `route_audio_matches.yaml` 与具体场景、事件类型、触发位置和期望意图进行绑定。当前配置中全局启用 `voice_lead_distance_m = 40.0` 的前置触发策略，用于为后续减速、转向和变道动作预留准备时间。

三类长路线场景的典型语音触发点如下：基础操控场景在约 `55m`、`145m`、`380m`、`1460m` 和 `2860m` 分别触发右转、左转、左变道、提速和减速指令；复杂避障场景在约 `280m`、`1090m` 和 `1720m` 分别触发行人避让、慢车超越和公交站谨慎通过指令；极限应急场景在约 `0m`、`1080m` 和 `2480m` 分别触发危险路况安全车速、突发加塞应急和施工并道指令。

标准测试流程如下。首先加载路线文件、场景配置和语音匹配文件，启动 `CARLA` 世界并挂载多视角相机、`LiDAR`、碰撞传感器和车道侵入传感器。随后系统按照固定步长执行主循环：先采集视觉、点云和车辆状态，再读取当前路线进度，判断是否满足语音触发条件；若满足，则写入语音事件、识别文本、识别意图、触发时间和触发位置；之后由场景控制器或代理策略输出控制量，执行一帧车辆控制；最后记录碰撞、违规、路线进度、动作完成情况和延时数据。测试结束后，再根据逐帧日志和事件检测器生成场景事件列表和结构化测试报告。

## 3. 指标计算方法

本项目测试报告采用“逐帧日志 + 事件检测 + 汇总统计”的方式计算核心指标。逐帧日志 `frames.jsonl` 记录每一帧的状态量和语音量；事件检测器根据成功条件和失败条件提取关键事件，如 `instruction_triggered`、`lane_change_completed`、`safe_slowdown_completed`、`safe_brake_completed`、`collision` 和 `task_failure`；报告生成器再在场景级别统计任务完成、违规次数、平均响应时间和子任务完成情况。以下给出核心指标的计算口径。

### 3.1 场景任务完成率

场景任务完成率用于衡量系统在某一测试场景或某一批次测试中的总体完成情况。对于单次场景运行，若事件列表中存在 `task_success` 且不存在 `task_failure`，则该次运行记为完成，完成值记为 `1`；否则记为 `0`。在多次重复测试条件下，场景任务完成率定义为：

`任务完成率 = 成功运行次数 / 总运行次数 × 100%`

对于单次运行内部的辅助统计，系统还记录路线完成率 `route_completion`，用于描述自车沿规划路线的最大完成比例，其计算方式为：

`route_completion = max_route_progress_m / route_total_length_m`

其中，`max_route_progress_m` 为测试过程中记录到的最大路线进度，`route_total_length_m` 为路线总长度。当路线完成率达到场景设定阈值，且所有强制子任务完成，同时无碰撞和严重违规时，该次测试才被记为任务成功。对于本项目三类长路线场景，场景成功不仅要求路线走完，还要求关键动作链全部闭环完成。

### 3.2 语音指令识别准确率

语音指令识别准确率用于评估语音输入在意图层面是否被正确识别。项目中每条语音样本都在语音匹配文件中配置期望意图集合 `expected_intents`，识别模块输出对应的 `recognized_intents`。若识别结果与期望意图在语义别名扩展后存在有效匹配，则该条指令记为识别正确。

在批量测试中的计算方式为：

`语音指令识别准确率 = 识别正确的语音指令数 / 语音指令总数 × 100%`

其中，“识别正确”采用事件级判断，而不是逐词完全一致判断。例如，`TURN_LEFT` 与 `LEFT_TURN` 视为同义匹配，`SLOW_DOWN` 与 `SLOW_DOWN_30`、`PEDESTRIAN_CAUTION` 在特定减速场景中允许按规则归并。该口径更贴近比赛对驾驶语义理解的要求，也能降低自然语言表述差异对统计结果的干扰。

对于无语音输入的对照测试轮次，则不纳入该指标统计；对于一条语音同时包含多个语义成分的组合指令，以主要事件绑定的期望意图集合为准进行判定。

### 3.3 多模态语义对齐精度

多模态语义对齐精度用于衡量“语音意图、场景事实和最终行为”三者的一致性。该指标与单纯的语音识别准确率不同，它要求系统不仅听懂指令，还要在正确的位置、结合正确的环境信息、执行正确的动作。项目中采用事件级对齐判定，满足以下三项条件的指令记为一次成功对齐：

第一，语音识别结果与场景期望意图匹配，即 `recognized_intents` 与 `expected_intents` 在语义归并后相容。  
第二，语音触发位置与场景动作窗口或锚点一致，即 `voice_trigger_progress_m` 落入对应事件的有效触发区间，或与场景锚点保持可接受的前置距离。  
第三，触发后执行结果与场景任务目标一致，即后续事件中出现与该语义对应的有效完成事件，如 `lane_change_completed`、`safe_slowdown_completed`、`safe_brake_completed`、`overtake_completed`、`bus_stop_pass_completed` 或 `long_route_completed`，且执行过程未被碰撞或严重违规中断。  

据此，多模态语义对齐精度定义为：

`多模态语义对齐精度 = 成功完成语义-场景-动作一致对齐的指令数 / 参与评估的指令总数 × 100%`

在实现层面，该指标可结合 `intent_match`、`voice_trigger_timestamp`、`voice_trigger_progress_m`、`expected_subtasks`、`action_success_rate` 以及场景关键事件共同计算。对于复杂组合指令，可按主要子任务链是否完整闭环进行判定；若只完成部分动作、触发位置错误或后续执行与感知环境冲突，则不计为对齐成功。

### 3.4 端到端决策响应延时

端到端决策响应延时用于衡量系统从接收到语音触发到产生可观测驾驶响应之间的时间开销。项目中同时记录两类延时：一类是语音后端自身的处理耗时，包括 `asr_latency_ms`、`parser_latency_ms`、`model_latency_ms` 和 `end_to_end_latency_ms`；另一类是场景级决策响应延时，即从语音触发到首个有效驾驶动作事件发生之间的时间差。

单条指令的决策响应延时定义为：

`response_latency_i = t(first_effective_action_i) - t(voice_trigger_i)`

其中，`first_effective_action_i` 依据场景不同可取 `lane_change_started`、`slowdown_started`、`emergency_brake_started` 或 `speed_target_reached` 等首个有效事件。批量测试中的场景平均响应延时定义为：

`平均响应延时 = (1 / N) × Σ response_latency_i`

最终以毫秒为单位输出：

`response_latency_ms = 平均响应延时 × 1000`

该口径与比赛要求的“端到端决策响应延时”一致，既考虑语义触发，又考虑系统是否真正输出了场景相关动作。对于极限应急场景中的突发加塞，报告还额外统计 `emergency_response_latency_ms`，用于专门考核应急制动开始的响应速度。

### 3.5 碰撞、违规与异常统计

碰撞、违规与异常统计用于衡量系统在完成任务过程中是否保持了车规级安全和交通合规性。项目中逐帧记录 `collision`、`lane_invasion`、`red_light_violation` 和 `route_deviation` 等布尔量，并采用“由假变真记一次激活”的方式统计事件次数，以避免同一连续事件被重复累计。

各项统计定义如下：

`collision_count = 碰撞状态由 0 变为 1 的次数`  
`lane_invasion_count = 车道侵犯状态由 0 变为 1 的次数`  
`red_light_violation_count = 闯红灯状态由 0 变为 1 的次数`  
`route_deviation_count = 路线偏离状态由 0 变为 1 的次数`  
`violation_count = lane_invasion_count + red_light_violation_count + route_deviation_count`

异常统计还包括任务失败原因和场景级异常标签。若测试过程中首先出现路线偏离、闯红灯、车道侵犯、碰撞、车道变换超时或到达测试结束仍未满足成功条件，则事件检测器会写入 `task_failure`，并记录 `failure_reason`。因此，异常分析既可以从次数层面统计，也可以从首个失败原因层面统计。该机制便于后续对“未成功的原因是感知失配、规则违规、控制失稳还是场景时序未满足”进行分层复盘。

通过以上指标，本项目能够对三类长路线场景中的语音理解、多模态决策、动作执行、安全合规和实时性表现形成可追溯、可量化、可复现的统一评测结果。
